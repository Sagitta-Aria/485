## 已确认的现象

用户反馈扫描经常在中途失败，并确认失败时有设备掉线后重新上线。

读取现有历史报告后，16:20 至 16:58 期间进入测量的 7 次扫描中有 6 次失败、1 次完整结束：

- 4 次为上位机流超时、停止完成未确认，分别保留 23、28、168+23、115 次读数；最终复位无错误。
- 2 次为 Master 明确回传 `TOPO_FAILED ... error=ESP_ERR_TIMEOUT local_reset=ESP_OK remote_reset=ESP_OK`，分别保留 15 和 10 次读数。
- 成功的一次保留 168 次编码读数及 24 次单点读数。
- 17:13:46 新增报告同样为流超时和停止完成缺失，保留 120 次编码读数。

这些故障在单点电阻显示更新前已经出现。失败端口和轮次不固定，正常 OL 读数不能解释任务中断。

## 原因与边界

固件在 TCP 断开时使扫描 epoch 失效；旧 worker 清理后不再回传旧会话的终止帧。重连后 `TOPO_ABORT` 可以回复命令已接收，但无法让已经退出的 worker 再发送 `TOPO_STOPPED`。

旧上位机没有把 Master 断线传给扫描控制器，仍等待旧流最多 90 秒，再等待停止确认最多 30 秒。离线连续 3 次复现出与历史报告一致的错误和部分读数。这是已确认的断线处理缺陷。

实际触发断线的是无线链路、ESP32 发送超时、设备重启，还是上位机 7 秒心跳门限，旧报告不能区分。两次固件主动报告的超时也可能发生在 RS485 或 Master 间通信。本次不宣称已经证明无线根因或解决所有中途失败。

## 本次修改

1. 网络线程直接投递被拓扑控制器接收的结果，其余结果维持已有界面队列路径。
2. 任一参与扫描的 Master 断开就使本次扫描失败；立即重连也不会复用失效会话。断线前已收到的样本保留，从机调试 WiFi 断开不会误取消扫描。
3. 源 Master 已断开时，不再等待不可能补发的旧任务终止帧；接收侧断开时仍停止源 Master。复位会在有限时间内等待设备重连或固件退出清理状态，失败则明确标记复位未确认。
4. 清理期间显示连接中断和复位状态，保持操作互斥；结束后提示重新扫描。
5. 上位机接收心跳等待从 7 秒调整为 15 秒。该调整增加短时停顿容忍度，不等于断线续扫，也没有改变 ESP32 的 2 秒发送超时。
6. 报告增加带时间戳的通信记录和断线原因，保留最近 20000 项及淘汰数量，帮助下一次故障区分连接与设备内部超时。

## 验证与继续工作

使用 Python unittest、原有模拟 Master、真实本地回环 TCP 和原生 Tk 窗口进行软件验证。回环 TCP 只绑定 `127.0.0.1` 的系统分配端口，不连接实物设备。

验证结果：

- `python -m unittest discover -s tests`：`Ran 171 tests`、`OK (skipped=2)`；两项固件 C 测试因缺少本机 C 编译器跳过，本次未重新构建固件。（注：这是当时的记录。现在缺少 C 编译器会**报错而不是跳过**，见 [测试与 C 编译工具链](tests.md)。）
- 真实回环 TCP 完成 168 次编码读数和一次 25.380 ohm 单点读数，全程不消费界面事件队列。
- 第 23 次读数后关闭并重新注册源 Master，扫描及时以 `CONNECTION_LOST` 结束，保留 23 次读数，两端复位确认，报告记录断线和重连。
- 复位发送失败、发送后立刻重连、固件复位忙、停止过程中源 Master 掉线等边界均有回归覆盖。
- 使用实际秒数模拟 8 秒接收静默：旧 7 秒门限触发 `heartbeat_timeout`；15 秒门限下保持在线并正常回复 `OK PONG`。这是容忍度对照实验，不是实物断线原因的证明。
