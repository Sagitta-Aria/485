# 编码扫描结束后的逐点补测

日期：2026-09-07。工程仅为 `D:\esp32\cable_tester_rs485`。

## 问题与行为

编码扫描结束后，部分行仍有大量“待确认右端口”。当前报告中的这种情况可能是编码与单点读数不一致，并不一定是这些端口从未测过。例如 `topology_20260907_210617_584171d1.json` 的 3 个左端口为 `INCONSISTENT`，每行保留全部 24 个右端候选。

现在增加“补测待确认 (N)”按钮。由用户选择是否执行，N 表示待测的左右端口对总数。编码扫描或此前的补测结束并保存报告后，有待补测项且原扫描两台 Master 都在线时启用；扫描、补测和清理期间禁用。按钮通过已有上位机硬件互斥入口启动，其他测试或手动命令尚未结束时不能占用矩阵。

## 测量范围

- 首次手动补测针对 `UNKNOWN`、`INCONSISTENT`、`SHORT_CANDIDATES` 的源端口，逐点覆盖原计划的全部右端端口。原编码可能有误，所以不能用原候选集继续排除某些目标。正常行保留。
- 每对只采样一次，不重跑 `TOPO_RUN` 编码任务，不应用二分重复次数。24 路右端、3 行异常时为 72 次；同一个右端口与不同源端口的测量分别计数。
- 新结果不依赖原编码筛选目标，所有确认导通的单点都加入结果；与原编码已知位不一致时仍保留 `INCONSISTENT`，不静默改为正常。
- 逐点覆盖后，待确认列表只保留未测或判定未知的端口。全部判定确定而编码仍矛盾时，待确认为空，但状态仍为“结果不一致”，详情明确显示矛盾。
- 再次点击只测上轮补测仍未确定的端口对，已确定的单点复用。停止后不会把未完成的位置当成断开；重新点击可继续这些位置。

补测沿用原扫描的两端身份、从机数量、导通/断开阈值、稳定时间和预期接线。用户在输入框中改变设置不会改变旧结果的补测配置，开始补测后界面恢复原参数。重新测量期间应保持原接线不变；若换线或改动接线，应新建完整扫描。

补测只验证选定的异常行，不是所有正常行的全矩阵复测。完成流程不等于接线合格，也不能保证仪表在任何接触或噪声条件下都正确。

## 会话与数据

每次补测使用新的会话与任务号，重新发现设备、建立接收端计划，使用现有 `TOPO_POINT` / `TOPO_POINT2` 单点命令。可靠固件仍遵循 Flash 提交、FETCH、SQLite 持久提交和 ACK 的顺序，保留 70% 暂停、低于 50% 恢复规则以及测量前后通路令牌检查。旧固件可用原单点协议，断线行为仍遵循兼容模式。

上次报告和 SQLite 文件保留。补测另存新的 JSON/CSV，合并原正常行和本轮补测结果；JSON 新增：

- `recheck`：`parent_session_id`、`parent_report`、`planned_pairs`、`completed_pairs`、`samples_per_pair=1`。
- `recheck_samples`：只记录当前会话新增的单点原始读数；`point_samples` 是合并后的当前单点结果。
- `point_rechecked_sources`：已进入手动逐点复核的源端口，使用从 0 开始的全局编号。
- `pending_recheck_count`：剩余可补测的端口对数量。
- 复核行的 `point_recheck_complete`、`point_recheck_measured`、`point_recheck_total`：判定是否全部确定、已经采样的端口对数量及整行端口总数。

`completed_pairs` 统计已采到读数的位置，即使读数本身未确定也算已采样；是否还需补测以 `pending_recheck_count` 为准。原 `code_samples` 沿用父报告的编码证据，当前 `raw_frames` 和当前 SQLite 只记录新会话，来源可通过父报告追溯。CSV 更新全部行的接线矩阵、状态、阻值和原始单点响应，与同名 JSON 配套使用。

待补测配置保存在上位机内存，仅对应最近一次已保存的编码扫描及其后续补测。新建扫描使旧入口失效；上位机重启后不自动加载历史报告操作硬件。控制器校验父会话和配置，拒绝过期或参数已被更改的补测请求。
