# 双端线缆拓扑扫描

本功能用于 `D:\esp32\cable_tester_rs485`。每侧支持 1～10 台从机，每台 24 组双触点；两侧数量可不同，界面默认各 7 台，默认值不代表已探测到这些硬件。

## 连接与职责

```text
上位机 -- WiFi -- master1 -- 独立 RS485 -- slave1 ... slaveN
                                                | 待测线缆 |
上位机 -- WiFi -- master2 -- 独立 RS485 -- slave1 ... slaveM
```

两条 RS485 总线不互连，两侧可以重复使用相同从机地址。两端 Y0～Y3 按同名连接，Y0、Y1、Y2、Y3 之间不能短接。测量使用 master1 的 XD31H；master2 的本地矩阵默认全断，不把第二个仪表接入共享总线。

上位机按所选方法生成恒重编码分组或二分区间任务、下发任务、解析接线及安排补测。master1 执行扫描状态机，通过上位机路由协调 master2 准备右端分组，等待确认后读取 XD31H；从机只执行本侧 RS485 掩码和清除请求。两块 Master 都使用新版固件时，测量结果先提交到 Flash，上位机分批读取并确认。正常运行只有两个 Master 连接上位机。

master1 本地 S1 固定路由如下；上电完成初始化后保持闭合，普通 `RESET` 和拓扑清理均保留这四点。

| master1 本地端口 | 总线 | 仪表端 |
|---|---|---|
| X0 | Y0 | I- |
| X1 | Y1 | V- |
| X2 | Y2 | V+ |
| X3 | Y3 | I+ |

master2 本地 S1 上电及复位后全断。从机复位后两片矩阵全断。因此，扫描停止后的“复位”不表示 master1 四条固定仪表通路被关闭。

master1 本地 X0～X3 是固定仪表端，不能作为普通线缆节点再次接到其他 Y（含 Y4）。
这会把测量总线相连，可能让实际约 25 Ω 的线缆读成 0 Ω。手动选线缆 G1 时应操作两侧从机。
新版上位机和主机驱动会拒绝上述固定引脚改接；旧程序已有残余选路时，对 **master1 本地**
执行 `RESET` 可清除额外闭合并保留固定四点，对 slave1 的 `RESET` 不会清除主机残余。
实测与修复记录见 [手动 G1-G1 零阻值诊断](PR_manual_g1_zero_resistance.md)。

## 单板配置

- `master/main/wifi_server.h` 的 `WIFI_DEVICE_ID` 分别按两块实物设置为 `master1`、`master2` 后构建；该 ID 同时决定固定路由，拓扑窗口必须左 master1、右 master2。
- 从机只在 `slave/main/board_config.h` 设置 `BOARD_SLAVE_MASTER_INDEX`（1 或 2）和 `BOARD_SLAVE_INDEX`（1～10），使用不带 `U` 后缀的十进制整数。WiFi ID 自动生成为 `m1-s1`～`m2-s10`，RS485 地址由本侧从机编号生成 `0x11`～`0x1A`。两侧第一台均为 `0x11`，同一侧按连续编号配置且地址唯一。
- 从机 `BOARD_SLAVE_WIFI_DEBUG_ENABLED=1` 开启调试（当前保留此设置），`0` 关闭。不同侧可以同时 WiFi 注册，主机模式的 RS485 目标和拓扑标签仍用本侧 `slave1` 等编号，从机模式选 `m1-s1`、`m2-s1` 等 WiFi 目标。兼容的旧 WiFi 名称 `slave1`～`slave10` 仅用于过渡，同名旧固件仍会冲突。
- 现有 RS485 是 UART1 TX GPIO17、RX GPIO18、DE/RE GPIO2、115200 波特率；master 的 XD31H 为 UART2 TX GPIO40、RX GPIO39、9600 波特率。以当前硬件接线和各自 `board_config.h` 为准。

每个从机的组标签为 `slave1-G1` 到 `slave10-G24`。一组是相邻两个 X 触点，共同接同一根芯线的一端；当前软件映射是：

| 组 | 矩阵 | 电流触点 | 电压触点 |
|---|---|---|---|
| G1～G12 | S1 | X0、X2、…、X22 | X1、X3、…、X23 |
| G13～G24 | S2 | X0、X2、…、X22 | X1、X3、…、X23 |

左端组接 I+/V+，右端组接 I-/V-。实物双触点若不是这种相邻配对，必须先调整并验证映射，不能把 48 个独立触点当成 48 根芯线扫描。

## 上位机操作

1. 启动 `python cable_tester_gui.py`，启动监听服务器并等待两个 Master 在线。
2. 点击“拓扑扫描”，左端选择 master1、右端选择 master2，分别填写实际从机数量。程序验证 Master 能力、固定路由和本侧从机在线位图；缺少从机或能力不符时停止，不直接进入测量。
3. 选择“拓扑编码”或“二分扫描”，默认拓扑编码；未知一对多接线可选二分扫描，无需填写分支数量。二分模式可设置“二分采样次数”为 1～10 次，默认 1 次；编码模式禁用此选项。设置导通上限、断开下限和稳定时间，默认分别为 50 ohm、100 ohm、1 秒；两阈值之间、通信异常和无效仪表响应均保留为未确定，默认阈值需通过实物验证。
4. “预期接线”可选直通、仅记录或 CSV。直通只比较两侧都有的同号端口；CSV 支持部分预期映射，未列出的源端口不做错接比较。
5. 点击“开始扫描”。结果表显示每个左端口的已确认右端口、单点电阻、编码结果或扫描方法、异常标记和待确认候选。电阻列按右端口列出读数；选中一行后，下方可滚动查看完整接线、电阻和原始响应。支持异常筛选，电阻未测的接线仍保留在筛选结果中。停止按钮会请求取消并清理两端矩阵。
6. 结束、取消或失败后，程序自动在 `reports/topology/` 保存 JSON 和 CSV；窗口的导出按钮可另存这些文件。JSON 保存扫描方法、阈值、每条接线的单点电阻及原始状态和协议帧，编码模式另有编码表，二分模式另有全部重复读数和冲突记录；CSV 包含接线矩阵、单点电阻及各行原始数据。

导入的预期 CSV 格式与导出的结果矩阵不同，表头必须为 `source,target`，例如：

```csv
source,target
slave1-G1,slave1-G1
slave1-G2,slave2-G3
```

## 扫描后补测待确认端口

编码扫描结束并保存报告后，若有“待补测”“未确定”或“结果不一致”的行，可点击“补测待确认 (N)”。N 是待测的左右端口对数量，不是去重后的右端口数。只有原扫描的两台 Master 都在线且没有扫描运行时按钮可用；未点击不会自动追加这一轮测量。

首次手动补测会对每个异常左端口逐个测量原计划内的全部右端口，各测一次，不重跑编码，也不受“二分采样次数”影响。异常行的原编码可能漏掉目标，所以不只复测编码给出的候选子集。正常行保留。例如 24 对 24 扫描有 3 个异常左端口，首次手动补测为 3 × 24 = 72 次。沿用原扫描的主机、从机数量、阈值、稳定时间及预期接线，不使用扫描后在输入框里另改的参数；开始补测时界面恢复原参数显示。补测前后应保持线束接线不变，否则旧结果与新结果无法作为同一线束状态比较。

补测后更新已确认目标、单点电阻和待确认列表；仍然无效、阈值不确定或尚未完成的端口保留未知，可再次点击，仅测剩余未确定端口对。已完成全部逐点判定但仍与旧编码矛盾时，该行保留“结果不一致”，待确认列表清空，详情显示“编码与逐点复核结果不一致”。此时没有遗漏待测端口，但仍需检查仪表读数、触点或原编码，不能将列表清空等同于接线合格。

每次点击建立新的测量会话，通过原来的 Flash/SQLite 确认机制传输，并另存 JSON/CSV；旧报告不覆盖。JSON 的 `recheck` 记录父报告与父会话、计划和已采样端口对数量，`recheck_samples` 只包含本轮新读数，`point_samples` 为合并后的当前结果。停止后保留部分结果；可靠固件网络重连可续传，旧兼容固件仍按原断线规则结束任务。

本按钮用于当前进程最近一次已保存的编码扫描及其后续补测；新建扫描或重启上位机会使旧补测入口失效，不会自动加载历史报告继续操作硬件。没有待确认项或二分扫描结果不提供此入口。实现及验证记录见 [扫描后逐点补测](PR_topology_pending_recheck.md)。

## 测量次数与结果

以下次数表及初筛说明仅适用于“拓扑编码”。二分扫描的次数随接线和补测结果变化。

| 每侧从机数 | 每侧芯线数 | 每源端编码轮数 | 正常初筛次数 |
|---|---:|---:|---:|
| 1 | 24 | 7 | 168 |
| 7 | 168 | 10 | 1680 |
| 10 | 240 | 10 | 2400 |

两侧数量不同，初筛次数为“左端芯线数 × 根据右端数量生成的编码轮数”。发现短路候选或不确定结果后，会追加逐点测量。编码已识别的唯一接线，还需各进行一次单点电阻测量；异常补测已取得的单点读数直接复用，不重复测量。进度区分别显示“编码初筛”“异常补测”“接线电阻”，初筛后按实际补测计划更新总次数。

例如，每侧一台从机，只有一条接线且编码无异常时，总计 168 + 1 = 169 次；24 条一一连接且无异常时，共 168 + 24 = 192 次。每侧 7 台且全部一一连接时为 1680 + 168 = 1848 次，每侧 10 台为 2400 + 240 = 2640 次。表中初筛数量不是复杂故障下的总次数或运行时间保证。

合法唯一编码给出单一跨端连接；与预期不同标记错接，多源共享目标标记目标重复。非法编码先生成候选，再逐点检查。取消后的未测端口和仍无法判定的单元格保持未知，导出 CSV 使用 `?`，不会补成断路或正常。

## 二分扫描

二分扫描对每个左端口检查整个右端范围。导通或未确定的区间继续拆成两半，两半均检查；只有单独选择右端口、确认导通后才列为已连接。找到分支后继续搜索，不假设一对一或一对四，也不限制分支落在哪块从机。

每次区间或单点判定执行所选次数的独立测量，默认一次。选择多次时，各次分类必须一致；任一未确定或分类不同都按未确定处理。单次模式保留该次读数及原始错误原因。搜索后排除已确认的目标，对剩余连续区间再测一轮。剩余区间导通、读数不确定，或父区间导通而子区间均无导通时，逐点复核相关区间。发生的矛盾保留在报告中，即使补测找齐分支也标记“结果不一致”；未完成或仍有未知单点时标记“未确定”。进度显示“二分确认”，实际次数包含所有采样。采样次数控制单次判定，不限制后续复查或补测再次访问该端口。

二分方式依赖稳定的分组导通判定。重复确认及剩余区间复查能发现偶发误判，但若分组读数在多次测量中持续错误地显示断开，仍可能漏支。选一次可减少采样和网络任务，选多次便于检查重复分类是否一致；次数多并不等于读数一定正确。软件测试验证搜索逻辑和故障处理，实际阈值、并联通路和仪表稳定时间需用实物验证，不能将完成状态理解为无条件准确保证。

两块 Master 都必须在 `TOPO_INFO` 中报告 `binary=1 reliable=1 cache_ready=1`。任一端不支持时明确报 `BINARY_UNSUPPORTED`，不自动改用编码扫描；Flash 未就绪时停止并报告 `CACHE_UNAVAILABLE` 及固件提供的具体错误码。旧版 Master 仍可按原兼容协议运行拓扑编码。

## 接线电阻与报告字段

“单点电阻 (ohm)”来自左右各选一个双触点组时的 XD31H 原始读数，保留三位小数显示。不会把分组扫描时的并联读数当成某条接线的电阻，也不进行自动扣零或既有矩阵校准补偿。因此它是当前端到端通路的未校准读数，并不保证等于线缆芯线本身的电阻。发生短路时，各端口间显示的也可能是整个短接网络的等效电阻。

单点复核仍使用同一导通/断开阈值：若超时、位于阈值区间，或结果与编码不一致，该行保留“未确定”或“结果不一致”，同时保留被复核右端口及读数。未测、测量失败和 OL 不显示为 0；真正的零读数显示 `0.000`。扫描完成仅表示扫描流程结束，不代表所有接线合格。

新版 JSON 使用 `schema: 2`，保留旧字段并新增：

- 顶层 `resistance_basis: "single_point_uncalibrated"`，说明阻值来源。
- 每行 `connection_resistances`：按右端口记录 `target`、`target_global`、`resistance_ohm`、`bit`、`reason`、`raw`、`raw_value`、`range_code`。包含已确认接线，也包含编码曾识别但单点复核失败的接线；是否确认仍以该行 `status`、`targets` 和测量 `bit` 为准。
- 无单点读数时 `resistance_ohm` 为 `null`、`reason` 为 `NOT_MEASURED`，不能用分组读数填补。所有异常补测数据仍在顶层 `point_samples`，包括未导通的候选。

CSV 保留原接线矩阵和原始响应列，并在末尾为每个右端口追加 `resistance_ohm:slave1-G1`、`resistance_status:slave1-G1` 等成对字段。阻值列只存数字，无数值时留空；状态列分别记录 `CONTINUITY`、`HIGH_RESISTANCE`、`THRESHOLD_UNCERTAIN`、`NO_CONTINUITY_OR_OVERRANGE`、`MEASUREMENT_ERROR`、`INVALID_NUMERIC_READING` 或 `NOT_MEASURED`。阻值是否存在和是否判定导通是两个独立信息。

单点电阻显示本身兼容已有 `TOPO_POINT` 固件接口；下面的 Flash 缓存续传则需要两块 Master 同时升级固件及分区表。更新后重新启动上位机再扫描，已生成的旧报告不会被改写。

两种方法的 JSON 都包含 `scan_method`（`coded` 或 `binary`）。二分模式的 `binary_samples` 保存每次原始读数及源端口、区间、重复次数位置和任务号，`binary_confirmation_repeats` 记录本次选定的 1～10 次；每行另有 `binary_complete` 和 `binary_conflicts`。二分模式不生成编码签名，`rounds`、`weight` 为 0，`codebook`、`code_samples` 为空。单次直接显示原始读数，多次分类一致时按阻值排序取中间位置的真实样本及该次原始响应，偶数次取中间两个中的后一个，不生成平均阻值。全部原始读数仍保留在报告和 SQLite 中。CSV 在既有列之后追加 `scan_method`、`binary_samples_raw`、`binary_confirmation_repeats`，重复分类不一致记为 `UNSTABLE_READING`。SQLite 会话配置也保存所选次数。

## 扫描中断与通信诊断

新版固件通过 `TOPO_INFO` 协商缓存能力。两端都支持时，扫描采用 Flash 缓存确认传输：每条数据带会话、连续序号、任务号及 CRC32，上位机核对并提交本地 SQLite 后才发送累计 ACK。设备只回收已确认数据所在的完整扇区；丢帧、损坏帧或丢失确认可从最后连续保存的位置补传，重复数据不重复计数。

缓存按专用数据区的实际占用计算，达到 **70%** 暂停采样，已确认数据回收后降到 **50% 以下** 才解除暂停，保留余量并避免反复启停。部分尾扇区在写满且全部确认前继续计入占用，因此收到 ACK 不代表立即擦除每一条记录。

Master 间控制仍经上位机转发，任一端 TCP 断开时暂停，等待两端重连后先恢复右端计划，再恢复左端采集。在读数写入 Flash 前还会核对右端通路令牌；测量中通路改变时重测当前点。当前实现支持网络重连期间保留任务并继续，但不支持断开上位机后独立完成整次扫描。

MCU 重启与 TCP 重连不同：已提交 Flash 的数据可以恢复，物理测量不自动接着运行。上位机进程重启或新建扫描发现旧缓存时，会先停止旧任务，将残留数据保存到 `reports/topology/sessions/` 的独立 SQLite/JSON 后确认回收，再开始新扫描。恢复文件路径写入主窗口日志及新报告 `recovered_sessions`，旧数据不混入新扫描行。若上次已确认部分的本地文件丢失，会用 `acknowledged_prefix_without_local_records` 明确标记缺失范围，不能恢复已被 Flash 回收的数据。

恢复旧缓存时，上位机先读取该会话 SQLite 中保存的主机和从机数量，通过 `TOPO_DISCOVER` 恢复主机重启后丢失的清理范围，再复位旧会话。清理使用旧扫描的数量；新扫描填更小数量也不能跳过旧从机。若主机仍保留活动任务，探测返回 `BUSY`，清理继续使用固件中的原任务范围。旧配置缺失时保留原有清理方式，不猜测数量；原从机缺失时明确停止并保留会话。这样可避免每侧仅 1 台时按默认 7 台清理超时，继而让手动 PING 一直返回 `ERR BUSY TOPOLOGY_SESSION`。该修复只需重新启动更新后的上位机。

任一端仍是旧固件时使用兼容传输：TCP 断开会作废原扫描会话，同一设备 ID 重连也不能续扫。上位机保留收到的读数，等待重连及复位确认后结束。新版固件若缓存初始化失败则明确报 `CACHE_UNAVAILABLE`，不会静默使用无缓存模式。

拓扑结果由网络线程直接交给扫描控制器，不依赖界面刷新。上位机心跳等待由 7 秒调整为 15 秒，容忍更长的短时通信停顿；这不会恢复已经中断的 TCP，也不会改变 ESP32 的发送超时设置。

JSON 报告保留 `schema: 2`，新增 `connection_error`、`transport_events` 和 `transport_events_dropped`。通信记录包含带时区的时间戳、距扫描开始的毫秒数、请求及结果、心跳、断线及重连；断线项保存设备 ID、原因、最后完整接收帧及其距断线时间。最多保存最近 20000 项，较早被淘汰的数量单独记录，原始测量读数不受此上限影响。常见原因：

| 原因 | 可确认的事实 |
|---|---|
| `heartbeat_timeout` | 上位机读取连接时长时间未收到数据，主动移除连接 |
| `peer_closed` | 对端关闭了 TCP；仅凭此项不能区分 ESP32 重启、无线断开或主动重连 |
| `socket_error` / `delivery_failed` | 连接读写失败，详细异常在 `detail` |
| `TOPO_FAILED ... ESP_ERR_TIMEOUT` | 固件报告任务超时；需结合 Master 间请求/结果判断是否还需要 RS485 日志 |

JSON 继续使用 `schema: 2`，还包含 `transfer_mode`（`durable_cached` 或 `legacy`）、`durable_session`（本地 SQLite 路径）、`durable_sequence`（最高连续保存序号）及 `recovered_sessions`。通信诊断最初的修复依据见 [扫描断线处理](PR_topology_disconnect_recovery.md)，当前缓存协议、分区和验证见 [Flash 缓存与断线续传](PR_topology_flash_resume.md)。旧报告不会被自动改写。

## 清理与限制

拓扑扫描与原有测试、手动矩阵命令互斥，开始前也会等待未完成的手动请求。停止服务或关闭窗口时，界面保留结果接收通路直到控制器完成取消和清理。任何未确认的清理都会记录在报告中，不宣称复位成功。从机拓扑 MASK 默认 30 秒不续期即清除，PING/STATUS 不续期；这是拓扑掩码租约，不是全部调试命令的统一定时复位。

分组算法依赖“组中至少有一条有效通路即判导通”的 OR 模型。实际并联通路、电阻、触点和仪表稳定时间会影响判定，必须用直通、错接、开路、多线短接实物验证，再确定阈值和时序。OL/超量程或“无跨端导通”不等于已经证明线缆内部物理断裂，也可能是接触问题或高阻。

结果描述端口间可达关系，不保证定位线缆内部短路位置，也不保证发现与另一端隔离的同侧短路。Y4 快速数字通断及比较器方案尚未实现；当前拓扑采样使用 XD31H。

## 构建与验证

缓存功能需分别升级 master1、master2 的固件和分区表；**从机两侧都不需要升级分区表**，因为 `slave/` 使用 ESP-IDF 默认单应用分区表（`CONFIG_PARTITION_TABLE_SINGLE_APP=y`，`CONFIG_PARTITION_TABLE_CUSTOM is not set`），目录下没有 `partitions.csv`。只有 `master/partitions.csv` 定义了自定义的 `topology` 分区。`master/partitions.csv` 在保持 NVS、PHY 和 1 MiB 应用分区地址不变的前提下，使用现有 2 MiB 配置内的剩余 960 KiB 作为拓扑缓存。不能仅烧录应用 bin 而遗漏分区表，也不需要整片擦除。当前 `WIFI_DEVICE_ID` 为 `master1`；master2 必须按其身份单独构建，不能烧入同一份 master1 镜像。

使用 ESP-IDF v5.5.4，分别在两个固件目录执行构建：

```powershell
cd D:\esp32\cable_tester_rs485\master
./idf.ps1 build
cd D:\esp32\cable_tester_rs485\slave
./idf.ps1 build
```

在工程根目录可执行 `python -m unittest discover -s tests -v` 检查算法、模拟传输和 GUI 路由。其中 4 个模块会编译固件 C 源码，需要本机 C 编译器；缺少编译器时这 4 个模块报错而不跳过，编译器探测顺序和指定方法见 [测试与 C 编译工具链](tests.md)。构建及软件测试不等于实机验证；本次实现未执行烧录或实物线缆扫描。
